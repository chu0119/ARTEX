# 部署手册（Linux 测试机 / 生产机通用）

本文记录**实测可用**的部署流程与踩过的坑。路径按测试机 `/opt/artex` 写，
生产机同构，换路径即可。

## 0a. 内网机安装：LAN 本地源配方（Kali 2026-10 实测，两次全流程）

直连 GitHub 下载大文件在内网测试机（Kali VM 等）上必然卡死。配方：**Windows 当源，Kali 拉本地**。

```bash
# ── Windows 侧（Git Bash）──
mkdir -p /c/Users/<you>/AppData/Local/Temp/r95 && cd /c/Users/<you>/AppData/Local/Temp/r95
gh release download v0.3.95 --repo chu0119/ARTEX --pattern "artex-0.3.95-linux-amd64.zip"   --pattern "install.sh" --pattern "SHA256SUMS" --clobber
# 本地比对 SHA256（与 SHA256SUMS 里的 linux-amd64 行一致才继续）
sha256sum artex-0.3.95-linux-amd64.zip

# 给 install.sh 打本地源补丁（⚠️ $REPO 是变量，sed/replace 后必须确认替换处数）
python - <<'PY'
import io
s = io.open("install.sh", encoding="utf-8").read()
old = 'https://github.com/$REPO/releases/download'
assert old in s, "anchor missing"
s = s.replace(old, 'http://<windows-lan-ip>:8124/v0.3.95')   # 记得拼版本路径
io.open("install.sh", "w", encoding="utf-8", newline="
").write(s)
PY

# ⚠️ 双层目录坑：原 URL 是 .../download/$VERSION/$zip，补丁把前半段换掉后 $VERSION
# 还会再展开一层 → 实际请求 <root>/v0.3.95/v0.3.95/<zip>。本地源必须建双层同名目录：
mkdir -p v0.3.95/v0.3.95 && cp artex-0.3.95-linux-amd64.zip SHA256SUMS v0.3.95/v0.3.95/

# 起源（端口被旧会话残留占用时：netstat -ano | grep 8124 按 PID 全杀再起）
python -m http.server 8124 --bind 0.0.0.0 &
# 自检（三个都要 200）：zip / install.sh / v0.3.95/v0.3.95/zip

# ── Kali 侧 ──
curl -sS -O http://<windows-lan-ip>:8124/install.sh && chmod +x install.sh
sudo ./install.sh --mode=binary
# Windows 侧 LAN IP 看 `ipconfig`（VMware NAT 网段一般是 x.x.x.1）
```

坑位清单：① install.sh 替换锚点必须断言存在（历史上有静默空转先例）；② 双层 $VERSION 目录；
③ 8124 跨会话残留进程；④ Windows 侧 curl 自检 200 ≠ Kali 侧可达——Kali 本机也要 curl 一遍；
⑤ 装完 `curl 127.0.0.1:8787/api/health` + `/api/version` 双验。

## 0. 前置

- 二进制来自 GitHub Release（CI 构建，7 个 asset）：
  `artex-<版本>-linux-amd64.zip` + `SHA256SUMS`。
- **必须校验 SHA256**，官方 `SHA256SUMS` 里对应行必须 OK 才部署。
- 下载走 GitHub API 的 asset URL（`Accept: application/octet-stream`），
  或 `browser_download_url` 跟随 302。**asset 名字不带 `v` 前缀**：
  tag 是 `v0.3.66`，asset 是 `artex-0.3.66-linux-amd64.zip`。

```bash
sha256sum artex-0.3.66-linux-amd64.zip
grep 'linux-amd64' SHA256SUMS | sed 's/  */  /' | sha256sum -c -
# → artex-0.3.66-linux-amd64.zip: OK
```

## 2. 停服务 → 换二进制 → 启服务

### ⚠️ 任务运行期间部署 = 掐断在跑的意图

`systemctl stop artex` 会取消所有在跑的 worker run，它们被落成
`blocked: context canceled`，**内容全部丢掉**（已写回的事实还在，但那一步
的探测没了）。实测 2026-10-21 连续部署两版，任务 4 的 8 个意图全被掐断。

**部署前先看有没有任务在跑**：

```bash
sudo -n -u postgres psql -d artex -tA -F'|' -c \
  "SELECT id, status, left(name,30) FROM tasks WHERE status NOT IN ('done','failed','timeout');"
```

有在跑的任务时，两个选择：

- **等它跑完**（推荐，改动不急时）
- **先优雅暂停**（让 worker 写回成果再停）：
  ```bash
  curl -s -X POST "$API/api/tasks/<id>/control" -H "Authorization: Bearer $TOKEN" \
       -H 'Content-Type: application/json' -d '{"paused":true}'
  ```
  等它进 paused 再 stop。

**万一已经掐断了**，用官方接口把 blocked 意图恢复成 open（worker 会重新领取）：

```bash
curl -s -X POST "$API/api/tasks/<id>/intents/rerun-blocked" \
     -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{}'
# → {"id":"4","queued":false,"reopened":8}
```

### 实际替换步骤

```bash
sudo -n systemctl stop artex

SRC=/tmp/artx-upload/unpack/artex-<版本>-linux-amd64
D=/opt/artex

# 二进制：先写 .new 再 mv -f，避免 ETXTBSY（正在运行的二进制写不进去）
sudo -n cp "$SRC/artex" "$D/.artex.new"
sudo -n chmod +x "$D/.artex.new"
sudo -n mv -f "$D/.artex.new" "$D/artex"

sudo -n cp "$SRC/artex-hostd" /usr/local/bin/.artex-hostd.new
sudo -n chmod +x /usr/local/bin/.artex-hostd.new
sudo -n mv -f /usr/local/bin/.artex-hostd.new /usr/local/bin/artex-hostd

# ★ skills 必须用「合并」写法：cp -r "$SRC"/skills/. "$D"/skills/
#   写成 cp -r "$SRC"/skills "$D"/ 时，目标 skills 已存在，GNU cp 的行为
#   不保证把每个子 skill 补齐——实测漏掉过 api-recon，而 DB 里三个 agent
#   都绑定了它，结果 worker/auto/pentest 静默拿不到这个能力。
sudo -n mkdir -p "$D/skills"
sudo -n cp -r "$SRC"/skills/. "$D"/skills/

sudo -n cp "$SRC/start.sh" "$D/start.sh"
sudo -n chmod +x "$D/start.sh"
echo "<版本>" | sudo -n tee "$D/.version" >/dev/null
sudo -n chown -R artex:artex "$D"

sudo -n systemctl start artex
sleep 7
sudo -n journalctl -u artex --since '30 seconds ago' --no-pager | grep -Ei 'listening|panic'
```

**部署后必查**：

```bash
sudo -n ls /opt/artex/skills/          # skill 数量应与 release 里一致
sudo -n cat /opt/artex/.version
```

## 3. 已知的环境事实

- **服务进程带着 `HTTP_PROXY` / `HTTPS_PROXY`**（systemd `Environment=`）。
  Go 里 `http.DefaultTransport.Clone()` 会继承这个代理——想「直连」必须
  **显式 `transport.Proxy = nil`**。本项目已有三处按这个约定写：
  `agent/provider.go`（LLM）、`traffic/traffic.go`（目标流量）、
  `server/proxypool_api.go`。
- **出网代理 `10.10.70.14:7897` 对部分站点不通**（实测 cisa.gov /
  services.nvd.nist.gov 会「CONNECT 200 后 TLS 握手 EOF」，而 github 正常）。
  直连这两个源是通的。
- 测试机到 GitHub 间歇性失败；本机 GitHub 需走 Clash 代理
  （`socks5h://127.0.0.1:7897`）。

## 4. 登录凭据

- 用户名固定 `ARTEX`；密码是 bcrypt hash，存在 `settings` 的
  `auth.password_hash`。
- **重置密码**：删掉那一行 → `POST /api/auth/init`（body `{"password":"..."}`）
  → 返回 token。`init` 用 `InsertSettingIfAbsent` 保证只能设一次。
- 改密码用 `POST /api/auth/change-password`（需要**旧密码** + 有效 token）。

## 7. 拦截规则自检（2026-10-22 整改后）

拦截规则在 **v0.3.78** 重新划过分层：内置规则不再是「一律 deny」，而是分成
**明令禁止**（直接拒绝，不调模型）/ **交给 Agent 研判**（模型裁决）/ **人工确认**
（转审批）。全新安装的库里应当是这个状态。

```bash
TOK=$(curl -s -X POST http://127.0.0.1:8787/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"ARTEX","password":"<密码>"}' | python3 -c "import json,sys;print(json.load(sys.stdin)['token'])")

# 规则总数与三种动作的分布
curl -s http://127.0.0.1:8787/api/intercept/rules -H "Authorization: Bearer $TOK" \
  | python3 -c "
import json,sys
rs=json.load(sys.stdin)['rules']
from collections import Counter
c=Counter(r['action'] for r in rs if r['name'].startswith('[内置]'))
print('内置规则总数:', sum(c.values()))
print('动作分布:', dict(c))
for r in sorted(rs, key=lambda x: -x['priority']):
    if r['name'].startswith('[内置]'):
        print(f\"  {r['action']:>5} | {r['name']}\")
"
```

**期望值**（全新安装）：

| 动作 | 条数 | 含义 |
|---|---|---|
| `deny` | 10 | 明令禁止：任何语境都不可逆且无合法渗透用途 |
| `judge` | 12 | 交给 Agent 研判：作用对象取决于上下文 |
| `ask` | 0 | 人工确认（v0.3.86 起：listener 启停规则已移除，目标工具从未实现；已部署实例残留的该条规则无害，可手动删） |

**逐条核对要点**

- 每条规则的 `timeout_enabled` 应为 `true`，且 `timeout_seconds` / `timeout_action`
  是**该规则自己的值**（研判类 90s/allow，硬禁类 30s/deny）。这在 v0.3.78 之前
  是死字段——界面显示 60s/deny，实际生效的是全局 180s/ask。
- 「数据外泄管道」规则应当**已启用**（`enabled=true`）。它此前默认停用，因为
  旧 pattern 会误伤 `curl 目标 | nc 自己的回连器` 这种正常回连；新 pattern
  只拦「@文件上传」。
- 「SQL DROP DATABASE / SCHEMA」与「SQL DROP TABLE / INDEX / VIEW」应当是
  **两条独立的规则**（旧版本是一条合并的 DROP 规则）。

**运行期行为验证**（需要配好 LLM profile，否则研判类规则会走失败策略）：

发一条会触发规则的任务，然后在「系统 → 拦截审批 → 历史」里看记录：

- 触发**明令禁止**的命令（如 `mkfs.ext4 /dev/sda`）→ 记录里 `decision_source`
  是 `rule`，理由是规则自带的 message，**没有 `[模型]` 前缀**（说明没调模型）。
- 触发**研判**的命令（如 `rm -rf /var/www/html`）→ 理由带 **`[模型]` 前缀**
  （说明走了模型裁决），且 `rule_id` 指向命中的那条内置规则。

平台没有「试匹配」的接口（规则只在真实工具调用时生效），所以只能这样观察。

> ⚠️ **升级已有实例前先备份数据库**。规则迁移（`intercept_builtin_rule_actions_v1`）
> 会改写 `intercept_rules` 表的 action/timeout/pattern 字段。它只改「仍是内置
> 默认值」的行（按 action + timeout 三元组 + pattern 判定），**用户自己改过
> 的规则不动**——但备份仍然必须做。

## 9. v0.3.80 起的版本自检：skill 与中间件工具

v0.3.80 加了 `vuln-hunting` skill（主动漏洞挖掘方法论）与「中间件协议」工具
分类。装完后可以这样确认它们真的生效了。

### 9.1 skill 是否真的被模型看到

skill 的文件在 `<安装目录>/skills/`，**可见性绑定在 DB**。两者任一不对，
模型就看不到这个 skill——而页面的 skill 列表来自 DB，**看不出文件解析失败**。

```bash
# 1) 文件在不在
ls -la /opt/artex/skills/

# 2) frontmatter 能不能被解析（name + description 都要有值）
#    没有 description 的 skill 在模型面前等于不存在
for f in /opt/artex/skills/*/SKILL.md; do
  echo "=== $f"
  sed -n '1,5p' "$f"
done
```

**v0.3.80 之前有个坑**：`skills/scopesentry/SKILL.md` 的 frontmatter 结束符被
写成了 `## name:`（而不是 `---`），norma 找不到 frontmatter 边界 → 整块 YAML
没被解析 → 那个 skill 从来没在模型面前出现过。v0.3.80 已修。

### 9.2 中间件协议工具

页面「系统 → 宿主环境」里应多出「**中间件协议**」一组，15 个工具：

MQTT gmqtt / paho-mqtt；消息队列 pika / amqpstorm / confluent-kafka / kombu；
数据库 pymongo / pymysql / psycopg2-binary / redis；SOAP zeep；
GitLab python-gitlab；网络设备 netmiko / napalm；SIEM splunk-sdk。

**装的时候注意**：这些是**纯库**（没有命令行入口），平台用

```bash

```

### 9.3 近期高危快通道

漏洞情报同步现在有两条线：**主同步**（全量目录）与**快通道**（按发布时间拉
最近 7 天、只收 CVSS≥9.0 或 CISA KEV）。快通道的游标独立，间隔默认 30 分钟。

```bash
# 快通道的游标与入库量
sudo -u postgres psql -d artex -tAc "
SELECT source, total_synced, left(coalesce(cursor,''),30), coalesce(last_error,'')
  FROM vuln_sync_state"
```

看到 `nvd_fastlane` 这一行有 `total_synced` 增长即说明快通道在跑。
若看到 `nvd rate limited`，那是 NVD 限速——两条线共享额度，平台已用闸门协调，
若仍超限则配 `NVD_API_KEY`（限速从 5 次/30s 提到 50 次/30s）。

## 10. 排障：网页打不开但「服务状态正常」

**症状**：`systemctl status artex` 显示 `active (running)`，但网页打不开。

**这在 v0.3.81 之前是个真问题**（现在已修，但排查思路仍然适用）：

- systemd 看到的是 **`start.sh` 这个包装脚本**还活着（它正在等 artex 子进程），
  而真正崩的是 artex 本体。所以状态是 running，**实际全挂**。
- 典型触发：数据库密码与 `config.json` 不一致、schema 迁移失败、端口被占。
  这些都是**永久性**故障，崩溃在无限重试中，首因被日志淹没。

**v0.3.81 起**：start.sh 连续 5 次异常退出就放弃自拉起，systemd 的
StartLimit 也会让单元进入 `failed (start-limit-hit)`。所以现在**状态会如实
显示故障**。

**排查步骤**：

```bash
# 1) 看真实日志（别只看 status）
sudo journalctl -u artex --no-pager -n 50 | grep -vE "collation|警告|描述|提示"

# 2) 看崩溃计数与放弃自拉起的提示
```

**改密码的正确做法**（别只改角色不改 config.json，反之亦然）：

```bash
# 改角色密码 → 同步改 config.json（两者必须一致）
sudo -u postgres psql -c "ALTER ROLE artex LOGIN PASSWORD '<新密码>'"
sudo python3 - <<'PY'
import json
p='/opt/artex/config.json'
c=json.load(open(p)); c['database']['password']='<新密码>'
json.dump(c, open(p,'w'), indent=2)
PY
sudo chmod 600 /opt/artex/config.json
sudo systemctl restart artex
```

> install.sh 在**角色已存在**时会用新生成的密码同步 `ALTER ROLE`（v0.3.79 起），
> 并把同一个密码写进 config.json——两者天然一致。
